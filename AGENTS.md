- Spaced repetition is tracked per skill via authenticated submitAnswer and service-only record_verified_answer; objective correctness is computed with shared answer helpers on the server and word_progress is derived. Flashcards remain explicit self-assessment pending approval to change that exercise. Why: browser correctness flags must not decide objective progress.
- Homework completion and continuation share homeworkStatus/buildHomeworkPractice over paginated reviews between assignment and deadline: each required exercise needs full 1x/2x coverage plus its success threshold; mixed QCM checks both directions. NULL requirements retain legacy 80%/60% thresholds. Why: student, teacher and parent reports must agree without extra result writes. Streak uses computeStreak with DAILY_GOAL.
- Teacher list folders: list_folders table (teacher-owned, RLS) + nullable vocab_lists.folder_id (ON DELETE SET NULL); sharing = copy_folder(share_code) security-definer RPC that deep-copies folder, lists and words to the caller. Why: deleting a folder never deletes lists; colleagues edit their own copy without reading others’ data.
- Written answers (typing & cloze) are validated by `isWrittenCorrect`: spaces never matter (extra/doubled/missing) and dead keys ¨ / " count as ä/ö/ü via `normalizeAnswer`; the article is still required. Speaking keeps `isAnswerCorrect` (spaces matter, punctuation stripped). Why: mobile keyboards add stray spaces; dead-key layouts type trémas as ¨ or ".
- Match game scores are derived by play_match_turn from owner-bound, locked match_sessions created by start_match_session; legacy record_match is disabled. Pairs feed streak/daily count but not homework or skill_progress. Why: students must not submit their own totals or replay completed pairs.
- Passwordless code login: students sign in with an 8-char code from public.student_codes + a 6-digit PIN, teachers with a username; both map to synthetic emails (s-<code>@eleve.vokabeln.local, t-<user>@prof.vokabeln.local, see src/lib/student-code.ts) with auto-confirm email enabled and HIBP off. Codes are created by generate_student_codes, linked in handle_new_user, checked pre-login by anon-callable check_student_code; annual reset = purge_class_data. Why: zero personal data (no e-mails) for students and teachers; never require real emails for new accounts.
- Student PIN login goes through the studentLogin server function (src/lib/student-login.functions.ts), which enforces lockouts from student_login_attempts (service-role only) via src/lib/login-lock.ts before returning a session. Why: brute-force protection must be server-side.
- Homework time: silent client timer (src/lib/study-time.ts, pauses when tab hidden or 60 s idle) adds seconds via add_homework_time RPC (≤120 s per call, own class only) into homework_time; only the homework's teacher can read it, students never see it. Why: teacher-only effort metric without trusting large client values.
- Review answers go through sendAnswer (src/lib/answer-queue.ts): network failures are queued in localStorage and replayed in order on reconnect; server refusals are not queued. Why: school Wi-Fi drops must not lose answers.
- Student training list selection uses class assignments and scopes the session query/pool to the selected list; homework links retain their explicit list. Why: training must not mix vocabulary from other lists or override assigned homework.

- Answers carry reviews.homework_id chosen server-side by pickHomeworkForAnswer (clicked homework containing the word, else the active one containing it that ends first; never archived; never refused because of a homework); tagged answers count only for that homework, even after its deadline (shown as late), untagged answers keep the created→due window. homeworks.coverage_rule=false keeps older homeworks on threshold-only completion (new ones default true). Homework word_ids are always frozen at creation (client + BEFORE INSERT trigger) so later list edits never change a homework. Why: each homework is independent and can be finished late.
- Duels: duels/duel_players have no direct table access; start_duel/duel_question/answer_duel/my_duels security-definer RPCs pick a random classmate, check answers and time server-side, and hide the opponent score until both finish. Duel answers are not written to reviews. Why: students must not forge duel scores, and duels must not affect homework.
- Quiz in class (quiz_sessions/quiz_answers): teacher drives state via RLS, students read via quiz_for_me RPC (answers hidden until reveal) and answer via answerQuiz server fn (server-checked, timed). Why: no forged scores.
- Avatar artwork uses shared MascotArt vector coordinates for body and accessory anchors; preserve stored outfit IDs. Why: wardrobe, duels and quiz avatars must stay aligned at every size without changing account data.
- Active student exercises share ExerciseViewport, measured below the app header against visualViewport, with flexible prompts and reserved answer space. Why: short screens and mobile keyboards must not push validation below the visible area.
